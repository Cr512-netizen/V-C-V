# Фаза M — многопоточность

Статус: к исполнению, 2026-10-23. Предшественники: B1, T (текстуры), W (генерация мира).
Задача фазы: перевести генерацию чанков и построение мешей на пул потоков с ограниченным числом рабочих, не потеряв детерминизм. Сетевой и физический параллелизм не входят.

## 1. Что есть сейчас и чем это плохо

- `core/jobs.h` — **4 строки**, `core/jobs.cpp` — **2 строки**. Класс умеет единственную операцию `parallel_for` и создаёт `enki::ITaskSet` на стеке. Ни `submit`, ни ожидания всех задач, ни числа потоков наружу нет.
- `world/chunk_manager.cpp` строит меш через `std::async(std::launch::async, ...)` **на каждый грязный чанк**. На MSVC это отдельный `std::thread` на чанк: правка одного блока на границе четырёх чанков создаёт четыре потока, а не использует уже существующий пул. При массовой правке (взрыв, разрушение) потоки создаются десятками.
- Стартовые девять чанков генерируются последовательно в `app/main.cpp`.
- `Jobs` не гарантирует, что задачи завершились к моменту разрушения: деструктор `enki::TaskScheduler` ждёт, но `std::function`, захваченные по ссылке, к этому моменту могут быть уже мертвы — сейчас это скрыто тем, что `parallel_for` всегда ждёт внутри себя.

## 2. Требования

1. **Детерминизм.** Результат параллельной генерации побайтово равен последовательному при любом числе потоков. Каждая задача пишет только в свой слот результата; общих счётчиков и накопителей нет.
2. **Ограниченный пул.** Число рабочих потоков задаётся конфигом (`threads`), `0` означает «сколько ядер», и зажимается в `[1, 64]`. Задачи не создают потоков сами.
3. **Никакого OpenGL на рабочих потоках.** Потоки только считают CPU-меши и воксели; загрузка в GPU остаётся в `drain_upload_queue_on_render_thread`.
4. **Живучесть при выходе.** `~Jobs` дожидается всех выданных задач; после деструктора ни одна задача не обращается к памяти владельца.
5. **Отсутствие регрессии по времени кадра.** Параллельная генерация 64 чанков не медленнее последовательной (замер в тесте с запасом), а построение мешей через пул не создаёт поток на чанк.
6. **Тестируемость.** Пул, `submit`, `wait_idle`, генерация и `ChunkManager` покрыты тестами M1–M8.

## 3. Модули и интерфейсы

### 3.1 `core/jobs.h` / `jobs.cpp` (переписывается)

```cpp
namespace nuc {
class Jobs final {
public:
    explicit Jobs(unsigned threads = 0);   // 0 -> hardware_concurrency, зажато в [1, 64]
    ~Jobs();                               // дожидается всех задач
    Jobs(const Jobs&) = delete;
    Jobs& operator=(const Jobs&) = delete;

    [[nodiscard]] unsigned thread_count() const noexcept;
    [[nodiscard]] std::size_t pending_count() const;

    void parallel_for(std::size_t count, const std::function<void(std::size_t)>& fn);
    void submit(std::function<void()> fn);   // «выстрелил и забыл», но с ожиданием в ~Jobs
    void wait_idle();                        // дождаться всех submit-задач

private:
    struct TaskSet final : enki::ITaskSet {
        std::function<void()> body;
        void ExecuteRange(enki::TaskSetPartition range, std::uint32_t thread) override;
    };
    void retire_finished();                  // освобождает завершённые TaskSet
    enki::TaskScheduler scheduler_;
    std::vector<std::unique_ptr<TaskSet>> owned_;
    std::mutex mutex_;
    unsigned threads_{};
};
}
```

- `parallel_for` — как раньше, но с проверкой `count == 0` (пустой диапазон не должен доходить до enkiTS).
- `submit` кладёт задачу в пул и сохраняет её во владеющем списке. Список чистится в `submit`, `wait_idle` и деструкторе: удаляются только наборы с `GetIsComplete() == true`, поэтому освобождение никогда не происходит на рабочем потоке под выполняющейся задачей.
- `submit` не потокобезопасен для одновременного вызова из нескольких потоков (один производитель — главный поток); это записано в комментарии к классу.

### 3.2 `world/parallel_chunks.h` / `parallel_chunks.cpp`

```cpp
struct ChunkRequest { std::int32_t chunk_x{}; std::int32_t chunk_z{}; };

// Генерирует чанки параллельно. Порядок результата совпадает с порядком запросов,
// поэтому вызывающий код не зависит от числа потоков.
[[nodiscard]] std::vector<Chunk> generate_chunks(Jobs& jobs,
                                                 const ChunkGenerator& generator,
                                                 const ResourceGenerator& resources,
                                                 std::uint64_t seed,
                                                 const std::vector<ChunkRequest>& requests);
```

Внутри: `results.resize(requests.size())`, `jobs.parallel_for(n, ...)` пишет в `results[i]` (каждый поток — в свой элемент), затем возврат. Руда накладывается тем же правилом, что и в `app/main.cpp`: биом берётся в центре чанка.

### 3.3 `world/chunk_manager.h` / `chunk_manager.cpp`

```cpp
explicit ChunkManager(ChunkMap& chunks, nuc::Jobs* jobs = nullptr);
```

- `jobs != nullptr` — построение меша уходит в пул: `std::promise<MeshUpdate>` + `jobs_->submit(...)`, `Pending` по-прежнему хранит `std::future<MeshUpdate>`, поэтому `drain_upload_queue_on_render_thread` не меняется.
- `jobs == nullptr` — прежний `std::async` (тесты и утилиты, которым пул не нужен).
- `ChunkManager` не владеет `Jobs` и не переживает его: это записано в комментарии.

### 3.4 `app/main.cpp`

Девять стартовых чанков генерируются через `generate_chunks(...)` с уже существующим `nuc::Jobs jobs(config.threads)`; `ChunkManager` получает `&jobs`.

## 4. Тесты (`tests/test_parallel.cpp`)

| Кейс | Что доказывает |
|---|---|
| M1 `parallel_for` посещает каждый индекс ровно один раз | 10 000 индексов, счётчик на индекс, сумма совпадает |
| M2 границы: `count = 0` и `count = 1` | пустой диапазон не падает, один индекс выполняется |
| M3 `submit` доставляет результат через `promise` | значение из задачи доходит до `future` |
| M4 исключение из `submit` доходит до `future` | `future.get()` бросает `std::runtime_error` |
| M5 `wait_idle` дожидается всех задач | 64 задачи с `sleep_for(1ms)` и атомарным счётчиком: после `wait_idle` счётчик равен 64, `pending_count() == 0` |
| M6 параллельная генерация равна последовательной | 16 чанков: воксели совпадают побайтово, порядок результатов совпадает с порядком запросов |
| M7 число потоков не влияет на результат | `Jobs(1)` и `Jobs(4)` дают одинаковые чанки |
| M8 `ChunkManager` через пул даёт тот же меш, что и синхронный | вершины и индексы совпадают с `build_chunk_mesh` напрямую |

## 5. Риски

| Риск | Смягчение |
|---|---|
| Гонка при освобождении `TaskSet` | освобождение только по `GetIsComplete()` и только на потоке-владельце |
| Задачи переживут `Jobs` и обратятся к мёртвым захватам | `~Jobs` вызывает `WaitforAllTasks()` до разрушения списка |
| Пул «съест» все ядра и кадр начнёт дрожать | число потоков из конфига, по умолчанию — `hardware_concurrency`, и никакого OpenGL на рабочих потоках |
| Параллельная генерация окажется медленнее из-за накладных расходов | M6 замеряет только корректность; время сравнивается вручную на 64 чанках и заносится в §6 |
| `submit` из нескольких потоков | запрещено и записано в комментарии; в проекте единственный производитель — главный поток |

## 6. Результат (2026-10-23)

| Проверка | Факт |
|---|---|
| `windows-release`: build + `ctest` | **144/144 passed** (M1–M9 плюс новые кейсы `Jobs`, прежние 134 без изменений) |
| Девять чанков, 1 рабочий против 4 | **4.55 мс** против **1.60 мс**, ускорение 2.8× (M9, замер на стартовом квадрате) |
| Детерминизм | M6: 16 чанков параллельно совпадают с последовательными побайтово; M7: `Jobs(1)` и `Jobs(4)` дают одинаковые воксели |
| Пул ограничен | `Jobs(1000)` зажимается в 64 потока, `Jobs(0)` берёт число ядер (кейс «thread count is clamped» в `tests/test_jobs.cpp`) |
| `ChunkManager` через пул | M8: меш из пула совпадает с прямым `build_chunk_mesh` по вершинам и индексам |
| Утечка задач при выходе | `wait_idle` после 64 задач оставляет `pending_count() == 0`; `~Jobs` вызывает `WaitforAll()` |
| Живой прогон приложения | старт без ошибок, 9 событий `chunk-load` дошли до модов, **143.6 FPS** (цель high-end — 144), скриншот `specs/img/parallel.png` |

Что оказалось не так, как задумано в спецификации:

1. **`enkiTS` не имеет `WaitforAllTasks`.** В v1.11 ожидание всех задач называется `WaitforAll()`, а `WaitforTaskSet` — устаревший алиас `WaitforTask`. Первая сборка упала именно на этом (`error C2039`).
2. **`Jobs::submit` не мог быть `std::function<void()>`.** `ChunkManager` передаёт в задачу лямбду с `std::unique_ptr` захватами, а `std::function` требует копируемого целевого объекта — MSVC выдал `static assertion failed: The target function object type must be copy constructible`. `submit` сделан шаблоном: вызываемый объект упаковывается в `std::shared_ptr`, а в пул уходит копируемая лямбда.
3. **Число потоков в enkiTS считается вместе с вызывающим.** `Initialize(n)` создаёт `n - 1` рабочих, поэтому `thread_count()` возвращает именно «участников», а не «рабочих»; в комментарии к классу это сказано явно, иначе легко получить на один поток меньше ожидаемого.
4. **Тест M9 намеренно не проверяет ускорение.** На загруженной машине сравнение времён — источник ложных падений, поэтому кейс утверждает только «параллельный вариант не медленнее, чем вдвое», а реальные числа печатает в лог и попадает в таблицу выше.
5. **`parallel_for` с малым числом элементов не дробится.** При `count < 8` весь диапазон отдаётся одной задаче: накладные расходы enkiTS на разбиение дороже самой работы.
